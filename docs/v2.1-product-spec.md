# v2.1 product — coarse indexes in JSON, heavy layers in light GPKG

Status: **SPEC, not implemented** (2026-09-19). Load when implementing the
`product_version: "2.1"` bump in `austria_processor.py` (fresh v2 + `--v2-upgrade`),
`v2_verify.py`, `kg_v2_store.py`, and the fast-path consumers in `app.py`
(`/api/v1/kg/<code>/heightfield`, future `/api/v3/trees`). Prereq reading:
`docs/v2-upgrade.md`, `segv2/README.md → v2 product design notes`.

## Why

* **Primary disk is the binding constraint.** Measured 2026-09-19: v1 `json/` = 22 GB for
  3464 KGs (avg 6.4 MB, 63330 = 12 MB) → ~54 GB at 8440, does not fit (48 GB free).
  `kg_json_v2.encode(63330)` = 0.72 MB (16.5×); ingest deletes the v1 file. The v2 upgrade
  IS the disk fix; v2.1 must not undo it.
* Downstream fast-path clients get nothing from the model bump alone:
  * `heightfield` (siedler-oesterreich) IDW-interpolates parcel/building centroids from
    the search index — 19570 has 63 samples for 2.3 km², forest/alpine cells are `null`.
  * `/api/v2/trees` (forestry.exe.xyz) reads DTM/DSM live from BEV per request; no product
    is used, so IDs/results depend on request-time BEV availability.
* Timing: only 8 upgraded codes + 7 fresh v2 KGs exist → redo is free. The expensive half of
  an upgrade is the full-GPKG pull (63330: 2.5 GB); everything below is seconds of CPU on data
  the peer already holds. A later second pass would re-download ~3000 × GB.

## Disk rule (hard)

> Per-tree, per-pixel, per-5 m data → `_light_v2.gpkg` on Zenodo (range-readable; primary
> uses `search_index.GpkgCache` LRU in `data/gpkg_cache/`, 0 resident cost).
> JSON / `kg_v2_store` gets only fixed-size coarse indexes, **≤ 25 KB per KG total**.
> No per-tree rows in `search_index.db` (8440 × ~50 k trees = 400 M rows). No polygons in
> JSON. No new per-parcel columns in the index.

## Additions

### JSON (`kgjson/2` blob — codec handles new sections generically, `_TABLE_PATHS` unchanged)

| section | content | budget |
|---|---|---|
| `product_version` | `"2.1"` (top level; also copy into the Zenodo manifest entry) | — |
| `terrain.grid25` | `{cell_m:25, cols, rows, origin:"nw", crs:"EPSG:3035", x0, y0, elev:<b64 gzip int16 delta-coded, dm>, slope:<b64 gzip uint8 deg>, nodata:-32768}`; computed from the 1 m DTM by block mean | 8–15 KB |
| `landcover.grid25` | same grid; `cls:<b64 gzip uint8 RLE>` dominant v2 segment type per cell; `legend:{code:type}`; `cover_frac:<uint8 0..255>` of dominant type | 2–5 KB |
| `acquisition` | `{tiles:[{tile, dtm_year, dsm_year, ortho_year, eff_date, years_gap}], summary}` via `als_acquisition.lookup` — table path already registered, just unpopulated | < 1 KB |
| `tree_stats` | add `apices_layer: "tree_apices"`, `n_apices`, `det_mode`, `algo_version` (=`tree_inventory.TREE_ALGO_VERSION`) | < 0.2 KB |

Derive grid25 from the same nDSM/DTM arrays the segmenter used (per tile → stitched), never
via a second raster read.

### `_light_v2.gpkg` (Zenodo only)

| layer | type | content |
|---|---|---|
| `tree_apices` | point, EPSG:3035, **with GPKG R-tree** | `tree_id` (`t_<E_dm>_<N_dm>`), `h_m`, `crown_r_m`, `crown_area_m2`, `detection_source` (ndsm/fused/ortho), `detection_conf`, `surface_class`, `tree_likelihood`, `stand_context` (tree/orchard/vineyard/hedge/garden/shrub — from the v2 segment the apex falls in), `segment_type_conf`, `dh_per_year_m` (multi-date DSM, flight-year-normalised, null if single epoch), `als_year`, `ndvi`, `leaf_type_hint` |
| `terrain_coarse` | 5 m tiled raster (int16) | bands DTM(dm), DSM(dm), nDSM(dm), slope(deg×10), aspect(deg); block mean of the 1 m grids |
| `segments` | existing | **add R-tree** (`gpkg_rtree_index` extension) |

`tree_apices` runs `tree_inventory.build_inventory` once per KG on the stitched nDSM
(`detection_mode=fused` when ortho RGBI present in the full GPKG, else `ndsm_only`; record
in `tree_stats.det_mode`), with the cadastre building mask and the v2 segment classes as
`classify_surfaces` inputs. Expected +30 s … 5 min CPU per KG; upload +1–3 MB.

## Eligibility / versioning

* `v2_upgrade_eligible(code)` → True iff `_json` + committed `_full_gpkg` AND (no `_json_v2`
  OR manifest entry `product_version < "2.1"`) AND strikes < max. Re-upgrading a code
  replaces `_json_v2` / `_light_gpkg_v2` (same keys; upload-then-swap under the Zenodo lock).
* Fresh v2 KGs emit 2.1 directly (`_is_v2` branch, ~`austria_processor.py:8725`).
* Director: `_compute_v2_upgrade_candidates` orders `product_version<2.1` codes after
  never-upgraded codes; `v2_priority` (currently `["63330"]`) still wins.

## Verify (`v2_verify.py`, +5 checks)

`grid25_dims` (cols/rows match bbox at 25 m ±1), `grid25_finite` (nodata frac ≤ tile-nodata
frac + 2 %), `grid25_range` (elev min/max within `terrain.elevation_{min,max}_m` ± 5 m),
`apices_layer` (light GPKG has `tree_apices` + R-tree, count within ±20 % of
`tree_stats.n_apices`), `product_version == "2.1"`. `verify_for_ingest` checks the JSON
subset only (no GPKG pull on primary).

## Primary store (`kg_v2_store.py`)

* `_MIGRATIONS` += `product_version TEXT`, `grid25 BLOB` (raw gz bytes of
  `{terrain.grid25, landcover.grid25}` — ~10–20 KB) so `heightfield` reads one small column
  instead of decoding the 700 KB doc (`_DOC_CACHE_MAX=24` only). Disk-neutral (the section is
  removed from the doc blob before storing, re-attached in `get()`).
* `stats()` gains `product_versions:{"2":n,"2.1":m}`; `/process.txt` `v2:` line shows `v2.1=m`.

## Fast-path API changes (`app.py`)

1. `GET /api/v1/kg/<code>/heightfield` — if store has `grid25`: bilinear-resample elev to
   the requested `cell` (≥ 25 m; `cell<25` → optionally `terrain_coarse` via `GpkgCache`),
   `source:"dtm_grid25_v2.1"`, plus `landcover:[[code]]` when `?landcover=1`. Else existing
   IDW path (`source:"idw_index"`). Response stays gzip/ETag'd.
2. `GET /api/v1/kg/<code>/landcover` — the class grid alone (siedler map cells).
